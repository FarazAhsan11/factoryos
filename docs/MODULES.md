# FactoryOS — modules

What is built, screen by screen, and the rules each one enforces. Moved out of
`CLAUDE.md` so it is read when you work on a module, not on every session; the
text is unchanged. For *how* a module is built and the patterns to copy, read
`IMPLEMENTATION_GUIDE.md` and `IMPLEMENTATION_GUIDE_2.md`. For the migration
behind a rule ("since `0033`…"), see `DATABASE.md`.

Auth, tenancy and factory setup are **built and working**; the first operational module has landed. Assume all of this is real before proposing to build it:

- **Auth** — login, password reset, invite → set-password flow, middleware session refresh, role-based routing.
- **Super-admin console** (`/admin`) — create / delete a factory (cascading wipe), branded email invites via nodemailer.
- **Factory workspace** (`/factory/[slug]`) — onboarding wizard gate, sidebar shell, dashboard.
- **The rail** (`FACTORY_NAV` in `src/lib/factory/nav.ts`) — sections **Operations / Quality & maintenance / Improvement / Plant setup**, holding links and expandable **groups**. A page that used to have a tab strip (Pipeline, Shift log, Resources, Admin) has **no strip now**: each of its screens is a group child linking to `?tab=`, and the workspace reads the tab with `useSearchParams` + its `resolve…Tab()`. The rail switches between screens of the open page with `history.pushState` (no round trip, nothing remounted — half-filled forms survive). UI names differ from route names: Production planning → Customer orders (`/products`), Batch pipeline / *Room* schedule (`/pipeline`; the Batch families screen is unwired — its component and queries remain, with no rail link or tab); Operations → Production log / Shift report (`/log`), Log history (`/data`), Floor status (`/floor`); Issues & CAPA (`/actions`); Breakdown maintenance (`/maintenance`); Kaizen ideas; Plant setup → Resources (Equipment register, Workforce) and Configuration (`/admin`: Company profile, *Rooms*, Process stages, Departments, Shift pattern). Italic names come from the factory's unit word. A new screen on a tab needs a rail child, not a strip; its tab-specific prefetch goes in `nav-prefetch.ts` keyed by the full href. Older mentions below of "tabs" / "Admin → X" / "the shift log's second tab" refer to these rail screens.
- **Admin & Settings** (`/factory/[slug]/admin`) — five working tabs: Company, Units, Processes, Departments, Shift times.
- **Resources** (`/factory/[slug]/resources`) — the two registers the rest of the plant names things from, on the same tab strip: Equipment (the machine register — number + name, `0028`) and Employees (invite + CSV import). They used to be Admin tabs; only where they live changed — same panels, same queries, same manager-and-up gate (add / remove people still needs admin). It sits under **Production** in the rail because they are day-to-day records, not one-time configuration.
- **Products** (`/factory/[slug]/products`) — the batch catalogue, its own item in the rail directly under **Pipeline**: a batch is raised here, with its customer order, and planned there. It was Resources' third tab (and an Admin tab before that); `/resources?tab=products` redirects here. Manager and up, same `ProductsPanel` and queries — the components still live in `src/components/factory/admin/`. Each product shows a **status**: **Received** from the moment it is added, until the batch has a card on the board, then the card's own Planned / In production / On hold / Finished, in the board's colours. It is derived by `productStatus()` in `product-queries.ts` from `pipeline_jobs.status`, **never stored** — the shift log already moves the card, and a copy on the product would be a second record of the same fact to fall out of step. Split by two pills — **Open**, meaning not yet planned or still on the board, and **Finished**, meaning every pipeline job for the batch is signed off; read from `pipeline_jobs`, not from the row's own Active / Retired chip). Since `0041` a product also carries the **customer order** it is made against — customer code and name, SO order no, order value, rep, order received, due date, expected start and finish. **Add product** is a dialog beside Bulk import (the inline strip it replaced could not hold fifteen fields), and both it and the row's **Edit** dialog (`EditProductDialog`, the pencil in the last column, Actions) render one `ProductForm`. There is no read-only detail view: the table shows every field as its own column — batch, product, product code, work order, status, required qty, customer, customer code, SO order no, order value, rep, order received, exp. start, exp. finish, due, planned for, added, actions — scrolling sideways with only the batch number pinned. The customer name fills in from a code the catalogue has already seen. Bulk import reads the same columns, matching headers after `normalizeHeader` with each column claimed once (`resolveHeaders` in `csv.ts`), accepts `30-Sep-24` dates as well as ISO (`parseDateCell`), and names any header it didn't recognise in the review.- **Shift log** (`/factory/[slug]/log`) — the entry form, activity feed, and amendments. The form has **three shapes**, chosen by the `category` set on the activity in Admin → Processes (`0030`): **downtime** asks for room, activity, start, end, batch and comments and nothing else — no quantities, no operators, no action flag; **preparatory** (mixing, drying, granulation) adds one quantity plus the unit the room counts in — batches / kg / litres / drums / containers / units, stored in `qty_unit`; **production** is the full record as before — equipment and speed on a machine stage, a target derived from speed × duration, actual and rejected quantities. `has_machine` and `has_output` survive as *derived* columns, no longer editable, so the pipeline trigger and every report keep reading what they always read. Two tabs and no page heading — the strip is the first thing on the screen: **Log entry** (the form, with the shift's activity feed beside it) and **Shift report**, which used to be its own nav item. Reading the sheet and correcting an entry are the same job done minutes apart, so they are one screen now; the report tab is supervisor and up (`logTabsFor()` in `log-tabs.ts`), and the heading and page width belong to the open tab rather than to the route. The entry pair is hidden by class, not unmounted, so a half-filled entry survives a look at the report. Log entry has a **Form view / Grid view** switch beside the tab strip (`?view=grid`, `LOG_VIEWS` in `log-tabs.ts`): the form is unchanged; the grid (`src/components/factory/log/grid/`) is every active room from Admin → Units, one editable line each, in room order. Each line is its own `useForm` over `logEntrySchema`, written through `createLogEntry` with the form's prefill (shift start clock, shift derived from times, product and target resolved, carry-over after a save) and the form's batch-gate wording — no second set of rules. Fields with no column (stage choice, slow reason) and every warning appear in a strip under the line only when needed; the speed unit is one combined select. Logging a line files it, shows it as a locked teal row above, and keeps the line open carrying the run forward; **Add row for …** gives a room a second line; Enter in a typed cell logs the line. Logged rows are shown for that sitting only — corrections stay in the feed and the shift report. The grid mounts on first use and is then hidden by class, like the form.
- **Data table** (`/factory/[slug]/data`) — server-side filter / sort / paginate over the shift log, CSV export.
- **Shift report** — one day, one shift, every room on one sheet. Rooms that logged nothing are *kept*, showing their pipeline status; it prints as a landscape handover document. Supervisor and up. It lives in the **shift log's second tab** (`/factory/[slug]/log?tab=report`); `/factory/[slug]/report` is now a redirect kept for old links and printed sheets.
- **Kaizen** (`/factory/[slug]/kaizen`) — improvement ideas from the floor and the queue that reviews them, under **Analytics** where Shift report used to be. It was the shift log's second tab, which put it behind a screen someone opens with a half-filled entry in front of them. Anyone may raise an idea; review is supervisor and up (`can_review_factory()`, `0019`). Components live in `src/components/factory/kaizen/`; the schemas stayed in the log's `schemas.ts`.
- **Pipeline** (`/factory/[slug]/pipeline`) — the batch board, plus **Batch families** and per-batch **stage planning**. The board is a **list, one row per batch** (`pipeline-board.tsx`; it was four Kanban columns): status as a coloured spine and chip, filtered by status and type, the arrow expanding a row to its stage strip and — for a bulk batch — its finished lots folded underneath; the name opens `JobDetailDialog`, **Stages** the plan, **+ Lot** New batch preset to that parent. Statuses move themselves from the shift log via a database trigger; nobody sets one by hand. Three ways in: **New batch** (a two-step dialog — pick manufacturing / packing / combined, then the batch itself *from the catalogue*, never typed — which can also write the batch's **stage plan** as a table (`StagePlanEditor`, `stagePlanSchema`) and **issue** it, and on Bulk Production raise a paired Finished Lot with its own plan; every part is validated before anything is saved, and a failure part way rolls back every job it created), **From catalogue** for adding several at once, or a `planned_for` date on the batch in Admin → Products, promoted onto the board when the page loads on or after that day (`promote_scheduled_jobs()`, migration `0018`). Since `0031` a job carries a **type** — stored as `manufacturing | packing | combined`, which is what the database's check and every guard read, but labelled **Bulk Production / Finished Lot / Single Batch** in the UI from `BATCH_TYPES` in the pipeline schemas; renaming a label is wording, renaming a value is a migration. A single batch carries both halves under one "Single batch details" block, in New batch and Edit batch alike — the bulk's (bulk unit, overage) and the lot's (pack size, pack unit, market) — because it is made and packed under one number; `createBatchJob` / `updateBatchJob` save `bulk_unit` and `market` for it too. Never a parent or a bulk received: the 0031 family guard refuses a parent on anything but packing, and `bulk_consumed` is gated on `batch_type = 'packing'` so it draws no allocation panel for bulk nobody gave it. Its **ordered quantity is shown, never typed**: it is `factory_products.required_qty`, and a second copy on the job would give the overrun check and the plan different numbers. When it is a packing run a job also carries a **parent** — the manufacturing batch whose bulk it draws on. That is what the Batch families tab reads: parent 46000 with children 46001/2/3 underneath, and a bar comparing Σ (children's containers × pack size) against the parent's bulk target. Over-allocation is badged, never blocked.

  The **Schedule** tab (`?tab=schedule`) is the plan read by room instead of by batch — the one arrangement the module could not produce, and the question a planner in front of the board actually has. Two views over one derivation (`buildRoomLanes` in `src/lib/factory/schedule.ts`), so they cannot disagree: **Board** is a calendar (`schedule-calendar.tsx`) — busy rooms down the side in name order, a fortnight across from this week's Monday (Prev / Today / Next move it a week), each stage a bar over the days `stageSpan` gives it: planned date to estimated finish, one day without an estimate, and a running stage at least to today (undated, it is drawn today). Solid is running, a tint is planned, and the colour is hashed from the batch so one batch reads the same in every room. **Queue** is the work surface, every stage in every room with its dates. Overlapping stages in one room are **stacked**, never drawn over each other; a day with two or more from today on is a **clash** — tinted red, the bars ringed, the room labelled "Clash · N days" — and `findRoomConflicts` (one per run of days with the same stages, from today, a year ahead) feeds a banner above the calendar whose **Show** moves the window to the clash and highlights the room. Past three stacked tracks a day says `+N more`, and a room's undated stages are a chip; both hand the room to the Queue, scrolled to it and ringed. A room with no work in the window offers a jump to its next (or last) dated stage. A room with nothing left to run is absent from both — a lane of dashes tells a planner nothing and twenty-five of them buries the four rooms that matter — and a stage with no room is counted and named rather than silently dropped. A running stage heads its lane whatever the calendar says. Clicking any card or batch number opens `StageEditDialog` (the whole stage, one form); the Queue's **Est. finish** and **comment** are edited in place instead, because a planner sets twenty of them in a sitting and a dialog per number turns that into five minutes. Both read the stages and jobs the workspace already holds, so the tab costs no extra request.

  Since `0033` each batch also carries a **plan**: one row per stage that produces something (Dispensing 500 kg → Compression 210,000 tablets → Coating → Packing), each with its own target and unit. The **last stage in the plan completes the order** — derived from position, so reordering moves it — and signing it off is what moves the card to Finished. Since `0038` the shift log accepts a `preparatory` or `production` entry only when four things hold: the typed batch number names a product, that product has a card on the board, the card is **issued for production** (issuing is itself refused until every stage has a target), and the activity is a stage in that batch's plan. Downtime is exempt from the last two — setup delays happen before issue, and no downtime activity is plannable — and needs no batch at all; but a number it *does* name must be real and on the board. The log resolves an entry to its stage automatically, and asks *which* only where a batch runs one activity several times (three packing runs, or three work orders under one number).

  Since `0037` each batch also carries a **tolerance** — a percentage, set on the New batch form beside priority and the due date, set once on the batch and inherited by every stage in its plan, never set per stage (the column allows an override; the app does not write one). It is the ceiling the shift log enforces: a stage planned for 20 kg at 5% accepts up to 21 kg, and an entry that would take it past that is **refused**, with the numbers that explain why. The stage's progress card in the log turns red as the quantity is typed, before the submit, and the plan's own bar and the card's stage strip go red for a stage left over the line by a tightened plan. Not the same knob as overage: that is extra deliberately made against the work order and only raises a flag.
- **Issues & CAPAs** (`/factory/[slug]/actions`) — the accountability loop. A flagged shift entry raises an issue, which then works through five stages — **Open → Investigating → Action taken → Verification → Closed**, one at a time, each move paid for with the evidence that stage produces, and since `0027` each stage collecting the thing it is *named after*: an owner, then a root cause, then the corrective (+ preventive) action, then the sign-off. Enforced by the `actions_stage_transition` trigger, not the UI. One legal skip: an **open** issue can be resolved straight to Closed by a supervisor when it needs no CAPA — it costs a written account of what was done (stored in `verification`) and leaves `investigating_at` null, which is what `resolved_direct` reads to label the text a *resolution* and draw the three middle stages as skipped (`0026`). Overdue and escalated are *computed*, never stored, and there are two clocks: the fix clock runs through Open, Investigating and Action taken, stopping once the corrective action is in, and a slower sign-off clock (`factories.escalate_hours`) runs through Verification.
- **Maintenance** (`/factory/[slug]/maintenance`) — the Breakdown Maintenance Request, all three sections of it. Report a fault against an equipment number (resolved to a name from the register), name the *initiating* department and the department *needed*, type the affected batch; requests are numbered `MR-2026-014` by a counter table. Opening one opens the document as **three tabs** — **Initiation → Engineering → QA review** — and the five statuses walk it: `reported → assigned → in_progress → completed → verified`, one at a time, forward only, each move paid for with what that section records. A name and a department to assign; nothing to start work (but that stamp is what makes downtime mean the machine rather than the paperwork); the work record plus the cleaning and production-review answers to complete; the change-control and deviation answers plus a signature to verify. Both yes/no pairs are tri-state — null is *unanswered* and the gate refuses it, because an unanswered box that prints as "No" is what the paper form gets wrong. Enforced by `maintenance_stage_transition` (`0029`), not the UI; supervisor and up may drive it, anyone may raise one. Response and downtime are computed in the view, never stored.
- **Deviations & NCRs** (`/factory/[slug]/deviations`) — the QA register, under **Accountability**, supervisor and up (`can_review_factory()` for raising and closing, `0044`). Three types and the type is part of the number: planned and unplanned deviations are `DEV-2026-004`, an NCR is `NCR-2026-001`. Specification, what happened, impact, raised by, QA reviewer, an optional linked CAPA; an NCR also takes a **disposition** (use as is / rework / reject / quarantine). One gate, **Open → Closed**, paid for with a QA name and a closing note — and for an NCR a final disposition that is not quarantine, because quarantine is a hold, not an outcome. A closed record is frozen. **Quarantine reaches past the module**: an open quarantine NCR puts the batch's card On hold (Quality), the shift log **refuses preparatory and production entries** against it until the NCR is closed, downtime is still accepted but never releases the hold, and after closing the next preparatory or production entry releases it — a rejected batch simply stays held. The board card, the job dialog, the log form and the grid name the NCR from `quarantine_no` on the board's view. The batch is typed and resolved to a product by the database trigger. Components in `src/components/factory/deviations/`, queries in `deviation-queries.ts`.
- **Floor status** (`/factory/[slug]/floor`) — every room as a card, from the **latest shift-log entry it filed on one calendar day**. First item under **Quality & maintenance**, everyone, read-only. The board is a day, not a shift: at midnight every card goes back to idle (the day follows `useRenderClock(todayKey)` until a past day is picked). A card is teal / running when its latest entry is preparatory or production, amber / stopped when it is downtime (then it also shows the stage the room was on before the stop), grey / idle when nothing was logged. Progress is the stage's `accumulated_qty` when viewing today, so it matches the dialog, and the entry's `accumulative` from `shift_log_entries_expanded` on a past day, so it reads as of then. Open-issue counts come from unclosed `actions` matched on `batch_no`. All / Active / Idle filter and Refresh sit top right; a live board refetches every minute. Clicking a card opens two tabs: **Batch progress** (the batch's whole plan, stage by stage, with the room's current stage ringed) and **Room schedule** (the plan's `unit_id` / `planned_date` read against a day that can be stepped backwards and forwards). Derivation in `floor-queries.ts` (`buildFloorRooms`, `roomSchedule`); entries are keyed under the shift log's prefix, so filing an entry refreshes the board, and jobs are read under `floorKeys.jobs`, not `pipelineKeys.all`, so the board page's promotion is never skipped. Components in `src/components/factory/floor/`.
- **Batch record** (`/factory/[slug]/batch`) — one batch, everything that happened to it, read-only. A debounced search over the catalogue (batch number, product, code or work order) opens a masthead and four tabs: **Activity** (every shift-log entry filed against the batch — named Activity, not Production, because a room's downtime and its mixing steps belong to the record as much as its production runs), **Issues** (the `actions` raised against it) and **Maintenance** (the requests naming it) and **Deviations** (the deviations and NCRs naming it, closable from `DeviationDetailDialog` as on their own screen). Counts sit on the tabs, so "were there any issues?" is answered without opening one. Cards open the modules' own detail dialogs — `ActionDetailDialog`, `MaintenanceDetailDialog` — so an issue worked from here is worked exactly as it is from Issues & CAPAs; the shift-log entry gets a read-only `BatchEntryDialog`, because corrections belong where the work is (the feed and the shift report both stamp who amended and why). Issues, maintenance and deviations are **matched on `batch_no`, not `product_id`**: both keep the number that was typed even when it matched no product, and matching on the id would drop the records most worth finding. Everyone may read it; it writes nothing.
- **Database** — 44 migrations in `supabase/migrations/`, with RLS on every tenant table.

Not built: a reusable **route on the product** that a new batch's plan is copied from (stages are planned per batch, as in the prototype); rework batches (the column `rework_source_id` exists, unused); attachments on a maintenance request ("attach additional documents" on the paper form — it needs a Storage bucket), the printable controlled-document view of a request, OEE & Downtime, Quality, Trends, signed handover reports, and the Pipeline's Gantt / Archive tabs (they render disabled from `pipeline-tabs.ts`). The shift log's Roster tab was dropped rather than deferred — the shift log has exactly two tabs now.
