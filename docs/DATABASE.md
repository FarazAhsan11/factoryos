# FactoryOS — database notes

Moved out of `CLAUDE.md` (text unchanged) so it is read when you touch a
migration, a trigger or a view. The migration files in `supabase/migrations/`
remain the source of truth; each opens with a comment explaining itself.

## Applying migrations

- SQL migrations live in `supabase/migrations/` (versioned, `NNNN_name.sql`). The Supabase CLI is **not** installed and there's no local DB connection string, so migrations are currently applied by hand via the **Supabase Dashboard → SQL Editor** (or a direct connection string if provided). Keep the migration files as the source of truth regardless of how they're applied.

## Migration-by-migration

- **44 migrations exist** (`0001`–`0044`). `docs/IMPLEMENTATION_GUIDE.md` §0 lists `0003`–`0014`; `docs/IMPLEMENTATION_GUIDE_2.md` §0 lists `0015`–`0017` and `0020`–`0025`. Check both before assuming a table or column is missing. `0018` adds `factory_products.planned_for` and `promote_scheduled_jobs()` — the scheduled route onto the pipeline board. `0019` adds `kaizen_ideas` and the `can_review_factory()` helper (supervisor and up, wider than `can_manage_factory()`). `0020`–`0021` turn Actions into the staged CAPA flow — see IMPLEMENTATION_GUIDE_2 §6a. `0026` adds the `open → closed` short road and re-bases the amendment guard on what was recorded rather than on the stage reached. `0027` splits the old Investigating gate in two — a fifth stage, `verification`, sits between `action_taken` and `closed`, the corrective action becomes the price of reaching it rather than of leaving Investigating, and rows already at `action_taken` are backfilled onto it (their `action_taken_at` copied to the new `verification_at`). `0028` adds `factory_equipment`, the per-tenant machine register — `equipment_no` unique per factory, resolved to a name in the shift log the way `batch_no` resolves to a product. `0029` fills in the rest of the maintenance request: the Section 2 and Section 3 columns, an `initiating_department_id` beside the existing "department needed", the `maintenance_stage_transition` gate, an update policy widened from `can_manage_factory` to `can_review_factory`, and a rebuilt `maintenance_requests_expanded` carrying the equipment name and the two computed clocks. `0030` classifies process stages: `factory_processes.category` (`downtime | preparatory | production`) replaces the editable `has_machine` / `has_output` pair as the thing that decides the shift-log form's shape, backfills it from those flags, and makes them derived through `factory_process_category_sync` — so a category and its flags can never disagree. It also adds `shift_log_entries.qty_unit` (a checked list matching `QTY_UNITS` in the log schemas) and rebuilds `shift_log_entries_expanded` to carry `process_category` and `qty_unit`. `0031` adds batch families: `pipeline_jobs.batch_type` (`manufacturing | packing | combined`), a self-referencing `parent_job_id` (`on delete set null` — removing a bulk card must not delete three real packing batches), the pack/bulk columns, and `pipeline_jobs_family_guard`, which holds the rules a `check` cannot see across rows: only a packing job has a parent, the parent is manufacturing and in the same factory, one level deep, pack size required, and a parent may not be re-typed while children draw on it. Deliberately **not** added: `ordered_qty` / `bulk_target_qty` — both are already `factory_products.required_qty`, and a second copy would give the overrun check (`0023`) and the family allocation different numbers. `pipeline_jobs_expanded` gains the type, the parent's batch number, `child_count`, `allocated_qty` (Σ children `required_qty × pack_size`) and `bulk_consumed`. `0032` makes `overage_pct` mean something: the shift log's over-production flag now measures against `required_qty × (1 + overage_pct/100)` rather than `required_qty`, so a batch told to make 4% extra is not flagged for doing exactly that, and `overrun_qty` counts from the allowance. `0033` is stage planning: `batch_stages` — one row per producing stage of one batch, with a target, a unit and an optional label / work order — plus `pipeline_jobs.issued_at`, `issue_job()`, and `shift_log_entries.batch_stage_id`. `is_final` is **derived from position** (the last row) by `batch_stages_final_sync`, and signing that stage off finishes the batch; `factory_processes.is_final_stage` and everything around it (the partial unique index, the produces-output check, `clear_other_final_stages`) is dropped. `shift_log_stage_guard` refuses a producing entry against an unissued batch, resolves the stage automatically when the batch runs the activity once, and asks which when it runs it several times; downtime is always allowed and always stores a null stage. `batch_stage_accumulate` keeps each stage's `accumulated_qty` equal to the good units logged against it. Both views were rebuilt: `accumulative` now partitions per **stage** (falling back to batch + process for rows with no plan), and the overrun target is the stage's where there is one. `0034` drops the `sequence_order` default — a column default is applied *before* BEFORE triggers, so the append in `batch_stages_validate` never ran and every stage sat at position 1 — and closes a hole in `batch_stage_transition` where a signed-off stage's yield answer could be rewritten through the no-status-change branch. `0035` adds `batch_stages.unit_id` (the room a stage is planned to run in — advisory, the log records where it actually ran) and `can_run_parallel` (the prototype's flag: a stage that may start before the one before it finishes, without which three packing runs off one bulk cannot be expressed except by lying about the order, which moves `is_final`), plus `batch_stages_expanded` resolving the process, room and signer names. `0036` replaces "the last stage finishes the batch" with **the final group**: the last stage plus every stage contiguously before it marked `can_run_parallel`. `batch_final_group()` walks it, `batch_stage_completes_job` finishes the batch only when every stage in the group is signed off, and `produced_qty` / `final_target_qty` in `pipeline_jobs_expanded` sum the group rather than reading one row — without which three packing runs off one bulk report `0 of 2,150` while 200 bottles sit on a pallet, and signing off the last run marks the order complete with the other two half done. A single-file plan has a group of one, so nothing about it changes. `0037` adds the **stage tolerance**: `pipeline_jobs.tolerance_pct`, set once on the batch, and a nullable `batch_stages.tolerance_pct` that overrides it — null inherits, so raising the batch's reaches every stage nobody overrode. `batch_stage_allowed_qty(target, tol)` is the one definition of the ceiling, shared by the guard and the view so the number refused and the number drawn cannot drift. `shift_log_stage_tolerance` (named to sort after `shift_log_stage_guard`, which is what resolves `batch_stage_id`) **refuses** a producing entry whose stage total would pass that ceiling, measured in good units so it agrees with `accumulated_qty`, and skips an update that moves neither quantity nor stage — so an amendment to a comment and the 0023 overrun clearance are never caught by a tolerance tightened afterwards. It is a hard block, unlike the soft over-production flag (`0023`/`0032`), because it fires while the entry can still be corrected rather than after the material exists; the sanctioned way past it is raising the stage target or its tolerance on the plan, which leaves `previous_target_qty` behind. **Do not merge it with `overage_pct`**: overage is extra deliberately *made* against the whole work order and raises a badge, tolerance is a bound on what may be *recorded* against one stage and blocks the write, and a plant can want 4% of the first with 0% of the second. `batch_stages_expanded` gains `tolerance_pct`, `effective_tolerance_pct`, `allowed_qty` and `is_over_tolerance` (reachable only by tightening a plan under entries already filed — which is when a progress bar must go red rather than read a contented 106%); `pipeline_jobs_expanded` gains `tolerance_pct`, appended at the end because `create or replace view` may not insert a column mid-list. `0038` closes the two ways round the shift log's gate: `shift_log_stage_guard` used to *accept* a producing entry whose batch matched no product, or whose product had no card on the board, filing it with a null `batch_stage_id` — so the least-planned work met the least enforcement, and the row could never afterwards be attached to a plan. Both early returns are now refusals, which makes the gate four rules deep for any `preparatory` or `production` entry: the number must name a product, the product must be on the board, the card must be issued, the activity must be in the plan. `downtime` is exempt from 3 and 4 and needs no batch, but a batch it names is held to 1 and 2 — a number nobody can look up is worse on a handover sheet than no number. The migration also contains the codebase's only `delete` against `shift_log_entries`, scoped to exactly the rows that came through the hole (non-downtime, null stage, no product or no card); pre-`0033` entries against batches that *are* on the board keep their null stage. **Do not add a delete policy** — that cleanup runs as the migration's owner. `0039` adds `batch_stages.planned_date` — the day a stage is planned to run, the *when* to sit beside the `unit_id` *where* 0035 added. Advisory in exactly the same way: nothing gates issuing on it and the shift log never checks an entry's `log_date` against it, because a stage slips a day or gets pulled forward when a machine frees up, and refusing the entry would put the plan ahead of the work. A `date`, not a timestamptz, for the reason `pipeline_jobs.due_date` is one — this plant plans in days and shifts. One column, not a start/end pair: a stage that genuinely spans days is already expressible through `can_run_parallel` and the accumulating total. `batch_stages_expanded` gains `planned_date` and a computed `is_behind_plan` (dated, unfinished, and the day has passed) — appended at the end, after the 0037 tolerance block, for the same `create or replace view` reason. `0040` adds the two fields a room queue asks for that a plan does not: `batch_stages.est_finish_date` (when the planner expects the stage off the room — an estimate, unlike `completed_at`) and `planning_note` (why a line sits where it does in the queue, distinct from the immutable `yield_notes` and from the batch's own `notes`). Deliberately **no** `est_finish_date >= planned_date` check: as a constraint it refuses the wrong field — a planner pulling a start date forward past a stale estimate would have the *start* rejected — so the rule lives in `stageEditSchema`, where the message can name both. Neither column gates anything; the queue is where they get filled in and has to be usable before they are. `batch_stages_expanded` gains both plus a computed `is_overrunning` (the estimate has passed and the stage is still on the room — a different failure from `is_behind_plan`, which means it never started). `0041` puts the sales order on the catalogue row: `factory_products.customer_code`, `customer_name`, `sales_order_no` (not unique — one order covers a bulk and its fill), `order_value` (numeric, null is "not recorded", checked `>= 0`), `sales_rep`, `ordered_on`, `due_date`, `expected_start` and `expected_finish`. The ordered quantity is still `required_qty` — no second copy. **`expected_start` is not `planned_for`**: `planned_for` is an instruction (it promotes the batch onto the board and refuses the past), `expected_start` is an estimate that moves nothing and is routinely already past when a sheet is imported. `due_date` is the customer's and `pipeline_jobs.due_date` the planner's: a new card's is **copied** from the product's on all three ways onto the board — `promote_scheduled_jobs()` (replaced in this migration, otherwise identical to 0018's), `createPipelineJobs` (From catalogue), and the New batch form, where it is read-only (shown locked beside priority, changed only in Products) — and never linked afterwards. No `expected_finish >= expected_start` check, for 0040's reason; the rule lives in `productSchema`. `productEditSchema` lets an edit *keep* a planned date that has since passed (0018 only refuses *setting* one), so a promoted batch's customer name can still be corrected. `0042` adds `factories.batch_model` (`single | split`, default `single`), the **batch number model** set in Admin → Company (`BATCH_MODELS` in the admin schemas). `single` — manufacturing and packing share one number — makes Pipeline → New batch ask for no type at all — every batch it raises is a Single Batch (the families view's "Add packing batch" preset still opens a Finished Lot); `split` — separate numbers — replaces the cards with two tabs, Bulk Production and Finished Lot, and never offers Single Batch. It shapes only the New batch dialog: no trigger refuses a `combined` job in a split factory, so From catalogue and `promote_scheduled_jobs()` still create jobs with the column default (`combined`), and switching models never strands existing cards. `0043` adds `factories.work_order_mode` (`none | batch | stage`, default `none`), **work order tracking** in Admin → Company (`WORK_ORDER_MODES`). `none` asks nowhere. `batch` shows a Work order field in New batch — prefilled from the product, blank falling back to the batch number — and writes it to `factory_products.work_order`, the batch's own row, rather than a second copy on the card. `stage` shows the per-stage `batch_stages.work_order` input in the plan dialog's `AddStageForm` and in `StageEditDialog`, and nowhere else. No new work-order column and nothing cleared on a switch: the setting decides what the forms ask, and `StageEditDialog` still loads and saves back a stage's hidden work order so one already on file survives. `0044` adds **Deviations & NCRs** — see IMPLEMENTATION_GUIDE_2 §17: `deviations` (numbered `DEV-`/`NCR-` through `next_document_number`, product resolved from the typed batch by `deviations_guard`, open → closed gate, closed rows frozen but for `on delete set null` references), `batch_quarantine_no(product)` as the one definition of "quarantined", `deviations_hold_batch` (an open quarantine NCR holds the card), and `shift_log_quarantine_guard` (refuses preparatory/production entries against a quarantined batch; skips an amendment that keeps batch and activity). It **replaces `pipeline_sync_from_log`** with two rules added: a downtime entry never releases *any* hold (a flagged issue's included — only preparatory or production work does), and nothing releases a hold while the batch is quarantined. `pipeline_jobs_expanded` gains `quarantine_no`, appended at the end. `0046` widens `pipeline_jobs.pack_size` from `numeric(10, 2)` to `numeric(14, 6)` — a 25 g fill against bulk in kg is 0.025, and two decimals stored it as 0.03 — dropping and recreating `pipeline_jobs_expanded` (unchanged from 0044) and the `pipeline_jobs_family` trigger, which pin the column's type. Show a pack size with `formatPackSize`, not the two-decimal `fmt`. `0047` adds `factory_products_expanded` — each catalogue row with its derived `status`, `status_label` and `is_finished` (every pipeline job signed off) — so **Customer orders is filtered, searched and paged on the server** (`fetchProductPage` in `product-queries.ts`, one page of one half at a time, `ProductsPanel` + `TablePagination`) instead of loading the whole catalogue. Status is still derived, never stored; the migration must be applied by hand or the table errors. The table is as tall as its page of rows and scrolls sideways only; counts, customer names and batch numbers (for the import) are their own small queries under `productKeys`.

## Core shape and invariants

- Core shape: `factories` and `profiles` (1:1 with `auth.users`, carrying `role` + nullable `factory_id`) from `0001`; per-tenant setup lists (`factory_units`, `factory_processes`, `factory_products`, `factory_shift_times`); `shift_log_entries`, the first operational table; and `pipeline_jobs` + `actions` / `action_notes`, both driven by triggers on the shift log.
- **Triggers on `shift_log_entries` are load-bearing.** Filing an entry moves a pipeline card (`pipeline_sync_from_log`) and can raise an action (`actions_from_log`). Both fire on `update` too, so amendments re-evaluate. If you add another, add its React Query key to the invalidation list in `log-entry-form.tsx` — see IMPLEMENTATION_GUIDE_2 §9.
- RLS helpers to reuse rather than re-derive: `is_super_admin()`, `current_factory_id()`, `can_manage_factory(uuid)`.
- **Shift-log entries are audit-protected**: no delete policy at all, insert requires `logged_by = auth.uid()`, and updates pass through the `shift_log_amend_guard` trigger, which demands an `amend_note` and forces provenance columns back to their originals. Never add a delete path. Since `0023` the guard also recognises an **overrun clearance** — an update touching only `overrun_note` / `_cleared_by` / `_cleared_at` — which needs no amend note, does not stamp `amended_at`, and is refused unless `can_manage_factory()`.

## Seed scripts and dev credentials

- Seed scripts: `node --env-file=.env.local scripts/seed-super-admin.mjs` (platform super admin), `node --env-file=.env.local scripts/seed-factory-setup.mjs <slug>` (demo units / processes / products for one factory), and `node --env-file=.env.local scripts/seed-stage-dates.mjs <slug>` (fills `batch_stages.planned_date`, and `unit_id` where a stage has no room, on plans already on the board, under one rule — **a room runs one stage a day**). A signed-off stage takes the day it was signed off and is never dated in the future — `--from` moves only work still to come. A roomless stage is put in a room this factory has already run that activity in, read from the other stages and the shift log, falling back to the quietest active room; a room somebody chose is never overwritten. Both invariants are re-checked on the finished schedule before anything is written. `--dry-run` prints it, `--force` re-dates rows that already have a date, `--no-rooms` leaves roomless stages alone. All idempotent.
